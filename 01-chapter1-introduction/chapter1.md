## 1.1 ที่มาและความสำคัญของปัญหา

Colorado Co., Ltd. เป็นธุรกิจจำหน่ายสินค้านำเข้าและสินค้า OEM ผ่านมาร์เก็ตเพลสอีคอมเมิร์ซในประเทศญี่ปุ่น กลุ่มสินค้าหลักได้แก่ สินค้าอุปโภคทั่วไปนำเข้า อุปกรณ์ตกปลาและเหยื่อล่อ สินค้ากลางแจ้ง และยาดมสูดสมุนไพร (ya dom) นอกจากนี้ยังอยู่ระหว่างพัฒนาสินค้าออริจินัลของตนเอง ได้แก่ อุปกรณ์ตกปลา สินค้าฟิตเนส กรอบรูปไม้ และสินค้าสำหรับงานฉลองครบ 100 วันของทารก

ธุรกิจเริ่มต้นเป็นธุรกิจเสริมตั้งแต่ปี 2009 และแยกตัวเป็นธุรกิจอิสระในภายหลัง โดยเจ้าของดูแลเองทั้งหมดตั้งแต่การวางแผนสินค้า จัดหา เจรจากับโรงงานต่างประเทศ การขาย การจัดส่ง ไปจนถึงบริการลูกค้า ปัจจุบันใช้ RSL (Rakuten Super Logistics) เป็นผู้ให้บริการ fulfillment หลัก กลุ่มลูกค้าเป็นผู้บริโภครายบุคคลที่ซื้อผ่าน Rakuten Ichiba เป็นหลัก (และจะขยายไป Yahoo! Auctions กับ Amazon ในเฟสถัดไป) กลุ่มเป้าหมายหลักคือผู้ใช้สินค้าตกปลา/กลางแจ้ง นักสะสมสติกเกอร์ และผู้ซื้อสินค้าอุปโภคทั่วไป

เนื่องจากทุกขั้นตอนหลังบ้าน (พิมพ์ label, เช็คสต๊อก, สั่งซื้อเพิ่ม, คำนวณต้นทุน) ยังทำด้วยมือทั้งหมด และเจ้าของเป็นผู้ดูแลระบบเพียงคนเดียว โครงการนี้จึงมุ่งพัฒนาเว็บ/ระบบจัดการหลังบ้านเพื่อทำงานที่ซ้ำซากและเสียเวลาให้เป็นระบบอัตโนมัติ โดยเลือก **Rakuten เป็นแพลตฟอร์มนำร่อง (เฟส 1)** ด้วยเหตุผลดังนี้:

- เป็นช่องทางขายหลักที่มีข้อมูลออเดอร์จริงให้ทดสอบระบบได้ทันที
- ใช้ RSL เป็นคลังสินค้าหลักอยู่แล้ว ซึ่งอยู่ใน ecosystem เดียวกับ Rakuten ทำให้เชื่อมข้อมูล order → stock → label ได้ลื่นไหลกว่า
- Rakuten RMS มี API รองรับการดึงออเดอร์ การจัดการ label template และการเชื่อมสต๊อก ซึ่งครอบคลุม 3 ฟังก์ชันหลักที่ต้องการ
- ลดความเสี่ยงจากการเชื่อมหลายระบบพร้อมกันในรอบแรก

## 1.2 ปัญหาที่พบ

จากการสอบถามเจ้าของธุรกิจ พบปัญหาหลักในการดำเนินงานประจำวัน 4 ข้อ:

1. **พิมพ์ใบปะหน้าพัสดุ (shipping label) ด้วยมือ** หลังได้รับออเดอร์ทุกครั้ง
2. **ต้องเช็คสต๊อกข้ามหลายช่องทางและหลายคลัง** (ในบริษัท + RSL) ด้วยตนเอง
3. **ตัดสินใจสั่งซื้อเพิ่ม (reorder) ด้วยความรู้สึก** ไม่มีเกณฑ์ที่ชัดเจน
4. **คำนวณต้นทุนที่แท้จริงของสินค้าแต่ละชิ้นยาก** เพราะต้องรวมหลายรายการ ได้แก่ ราคาซื้อ อัตราแลกเปลี่ยน ค่าขนส่งระหว่างประเทศ ภาษีนำเข้า ค่าธรรมเนียมมาร์เก็ตเพลส ค่าส่งในประเทศ และค่าธรรมเนียม RSL

งานที่ซ้ำซากและเสียเวลาที่สุดคือลำดับขั้นตอน: **เช็คออเดอร์ใหม่ → พิมพ์ label → เช็คสต๊อก → เตรียม reorder → คำนวณต้นทุนสินค้า**

ปัญหาเหล่านี้เคยส่งผลกระทบจริงต่อธุรกิจ เช่น

- Binder เก็บสติกเกอร์ล็อตแรก 500 ชิ้น มีของเสียประมาณ 20 ชิ้น ต้องแก้ไขสเปค (ความหนาปก, ระบบล็อค, มาตรฐานรู, สี)
- ค่าส่งในบริษัทเองอยู่ที่ประมาณ 600 เยน เทียบกับคู่แข่งที่ประมาณ 200 เยน ขณะที่ RSL คิดค่า picking ประมาณ 60 เยนต่อชิ้น จึงต้องหาสมดุลระหว่างต้นทุนขนส่งกับกำไร

## 1.3 วัตถุประสงค์

ผลลัพธ์สำคัญที่สุดของโครงการคือการสร้างระบบอัตโนมัติ 3 อย่าง สำหรับออเดอร์ Rakuten:

1. **พิมพ์ shipping label อัตโนมัติ** ทันทีที่ได้รับออเดอร์จาก Rakuten
2. **สั่ง reorder อัตโนมัติ** เมื่อสต๊อกต่ำกว่าเกณฑ์ที่ตั้งไว้
3. **คำนวณต้นทุนที่แท้จริงต่อหน่วยของสินค้าแต่ละ SKU** ได้ง่ายและแม่นยำ

ตัวชี้วัดความสำเร็จภายใน 3 เดือนหลังเปิดใช้งาน ได้แก่

- ออเดอร์ Rakuten ใหม่ทุกออเดอร์ได้ label ที่ถูกต้องโดยอัตโนมัติ
- สต๊อกต่ำกว่าเกณฑ์ทริกเกอร์ reorder ที่ถูกต้องโดยอัตโนมัติ
- คำนวณต้นทุน/กำไรต่อหน่วยได้เร็วและสม่ำเสมอ
- ลดขั้นตอนมือ ลดข้อผิดพลาดในการจัดส่ง และลดของขาดสต๊อก

## 1.5 ขอบเขตการทำงาน

**ขอบเขตของเฟส 1:** ครอบคลุมเฉพาะ Rakuten Ichiba + Rakuten RMS + RSL (Rakuten Super Logistics) เท่านั้น แพลตฟอร์มอื่น (Yahoo! Auctions, Amazon) จะพัฒนาในเฟสถัดไป ไม่รวมอยู่ในเฟสนี้

**สิ่งที่อยู่นอกขอบเขตของเฟส 1 (Out of Scope):**

- การเชื่อมต่อ Yahoo! Auctions
- การเชื่อมต่อ Amazon (SP-API)
- ระบบแจ้งเตือน/สื่อสารกับลูกค้าโดยตรง (ยังคงผ่านช่องทางแจ้งเตือน/inquiry ของ Rakuten ตามเดิม)
- ฟังก์ชันรับชำระเงินภายในระบบ (การชำระเงินของลูกค้าดำเนินการผ่าน Rakuten ทั้งหมด)
- Mercari Shops (เลิกใช้งานแล้ว — ไม่รวมในทุกเฟส)

**สิ่งที่ยังคงทำด้วยมือ (นอกขอบเขตของระบบอัตโนมัติ):** วางแผนสินค้า จัดหา เจรจาโรงงาน การตัดสินใจด้านคุณภาพ การอนุมัติขั้นสุดท้าย และกรณีลูกค้าพิเศษ — เจ้าของยังคงเป็นผู้กำหนดกฎ (label rule, threshold, supplier, order quantity, cost formula) และสามารถหยุดหรือแก้ไข action อัตโนมัติได้ทุกเมื่อ

**ผู้ใช้งานและสิทธิ์:** ผู้ใช้หลักคือตัวแทนบริษัท (เจ้าของ) ซึ่งดูแลทั้งระบบและตั้งค่ากฎทั้งหมดผ่านบัญชี Admin เพียงบัญชีเดียว บุคคลภายนอก (RSL, โรงงาน/ซัพพลายเออร์ต่างประเทศ) ยังคงสื่อสารผ่านช่องทางเดิมของแต่ละฝ่าย ไม่ผูกเข้าระบบโดยตรงในเฟสนี้ ส่วนลูกค้าปลายทางสั่งซื้อผ่าน Rakuten Ichiba ตามเดิม ไม่มีการสร้างระบบหน้าบ้านสำหรับลูกค้า

## 1.7 ประโยชน์ที่คาดว่าจะได้รับ

เมื่อระบบเปิดใช้งานและบรรลุตัวชี้วัดความสำเร็จตามข้อ 1.3 แล้ว คาดว่าธุรกิจจะได้รับประโยชน์ดังนี้

- ออเดอร์ Rakuten ทุกออเดอร์ได้รับการพิมพ์ label ที่ถูกต้องโดยอัตโนมัติ ลดเวลาและความผิดพลาดจากการพิมพ์ด้วยมือ
- ระบบแจ้งเตือนและสั่งซื้อสินค้าเพิ่ม (reorder) โดยอัตโนมัติเมื่อสต๊อกต่ำกว่าเกณฑ์ ลดปัญหาสินค้าขาดสต๊อกและลดการตัดสินใจด้วยความรู้สึก
- คำนวณต้นทุนและกำไรต่อหน่วยสินค้าได้รวดเร็วและสม่ำเสมอ ช่วยให้เจ้าของตัดสินใจด้านราคาและการสั่งซื้อได้แม่นยำขึ้น
- ลดขั้นตอนที่ต้องทำด้วยมือในงานประจำวัน ทำให้เจ้าของมีเวลาไปโฟกัสกับงานที่สร้างมูลค่าสูงกว่า เช่น การพัฒนาสินค้าใหม่และการเจรจากับโรงงาน
- วางรากฐานระบบที่พร้อมขยายไปยังแพลตฟอร์มอื่น (Yahoo! Auctions, Amazon) ในเฟสถัดไปได้ง่ายขึ้น
