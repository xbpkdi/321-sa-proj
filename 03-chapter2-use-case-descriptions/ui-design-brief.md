> ไฟล์นี้สรุปผลคุยกันจนจบแล้ว (ไม่มี TBD เหลือ) ใช้ brief นี้ไป prompt session "Claude design" ได้เลย

## 1. ขอบเขตงาน (อ้างอิง rubric ข้อ 29/30/31)

- **Site map / UI structure** (ข้อ 29): แสดงเป็น tree โดย root = หน้า Login (1A) แตกกิ่งไปยังหน้าจอของ actor แต่ละคน
- **User Interface design** (ข้อ 30): rubric เขียนไว้ว่า "8 screen (ไม่นับ Login) + Login = 9 หน้า" แต่หลังเช็คกับ diagram ที่ทำไว้จริง (sequence/collaboration) พบว่ามี Admin-facing screen มากกว่านั้น — **ยึดตาม diagram จริงเป็นหลัก** (รูบริก #18/#23 ต้องการให้ UI สอดคล้องกับ diagram 100%) รวมทั้งหมด **12 หน้า**

## 2. กฎสำคัญ: Content ต้องตรงกับ Use Case Description

## 3. App Identity

- **ชื่อระบบ**: RSL Fulfillment Hub — โชว์ใน topbar ทุกหน้า
- **ภาษาเนื้อหา**: ภาษาไทยทั้งหมด (sidebar, หัวตาราง, label ทั่วไปที่ไม่ได้ถูกกำหนดไว้ใน UC ก็ให้เป็นไทย เพื่อให้สอดคล้องกับเนื้อหาหลักที่มาจาก UC)
- **ปุ่มสลับภาษา (TH/EN)**: ต้องมีปุ่มสลับภาษาใน topbar **ทุกหน้า** (เหตุผลทางธุรกิจ: อาจารย์ผู้ตรวจเป็นคนไทย แต่ผู้ใช้งานจริงเป็นคนญี่ปุ่นที่อยากได้ระบบภาษาอังกฤษ)
  - Scope รอบนี้: ใส่ **ปุ่ม/UI element** สลับภาษาไว้ทุกหน้าเพื่อแสดงว่าระบบรองรับ i18n แต่ **mockup เน้นทำเนื้อหาเต็มเฉพาะภาษาไทย** ไม่ต้องแปลทุกหน้าเป็นอังกฤษให้ครบในรอบนี้ (ลดงานซ้ำซ้อนสำหรับ deliverable ของบทนี้)

## 4. Design System

> ℹ️ **ฉบับโค้ดจริง (Next.js) เปลี่ยนไปใช้ token สีจาก Atlassian Design System แล้ว** — ค่าที่ใช้จริงและเหตุผลอยู่ที่ `01418321-final-project-quark/DESIGN.md` ซึ่งเป็นแหล่งความจริงด้านสีและฟอนต์แทนหัวข้อ "สีหลัก" และ "Font" (สองหัวข้อนั้นคงไว้เป็นบันทึกช่วง prototype)

### สีหลัก (Palette)
หน้าตา component/layout หลักยึดตาม shadcn/ui (ข้อ 6.1) ส่วนลูกเล่น ticker/flip-board หยิบมาจาก `chula.hackathon.team1.quarkhadron.dev` (ข้อ 6.3) แต่เปลี่ยนโทนสีทั้งหมด — **ห้ามใช้ดำ/แดงแบบเว็บต้นแบบ**

- พื้นหลังหลัก: ขาว/เทาอ่อนมาก (เช่น `#FFFFFF`, `#F8FAFC`)
- สีเน้น (แทนที่แดงในเว็บ ref): น้ำเงินเข้ม เช่น `#1E3A8A` (ใช้กับปุ่มหลัก, ป้าย LIVE-style, เส้นขีดเน้น, ลิงก์)
- ตัวอักษรหลัก: เทาเข้ม/เกือบดำ เช่น `#1E293B`

### สี Status Badge
ไล่สีตามกลุ่มสถานะ จากการสำรวจ status ทั้งหมดใน use case description:

| กลุ่ม | สี | สถานะที่เข้ากลุ่มนี้ |
|---|---|---|
| รอดำเนินการ | เทา | รอตรวจสอบคำสั่งซื้อ, รอจับคู่กฎ SKU, รอ Admin ตัดสินใจสั่งซื้อ, รอสั่งซื้อจาก Supplier, รอตรวจสอบสต๊อก, รอส่งคำสั่งซื้อ, ยังไม่ได้จับคู่, รอจัดรูปแบบใบปะสินค้า, รอพิมพ์ใบปะสินค้า, รอส่งมอบ, รอแจ้งเลขติดตาม |
| กำลังดำเนินการ | น้ำเงิน | พิมพ์ใบปะสินค้าแล้ว, อยู่ระหว่างจัดส่ง, แจ้งเลขติดตามแล้ว, สั่งซื้อแล้ว |
| สำเร็จ | เขียว | จัดส่งสำเร็จ |
| ต้องระวัง/ทำเอง | ส้ม | รอดำเนินการพิเศษ, รอดำเนินการด้วยตนเอง, จัดส่งไม่สำเร็จ, ตีกลับ/คืนสินค้า |
| ยกเลิก | แดง | ยกเลิกแล้ว, รอยกเลิก Order |

### Font
**Noto Sans Thai** (โหลดจาก Google Fonts) สำหรับอักษรไทย — ฉบับโค้ดจริงจับคู่กับฟอนต์ละตินตาม `DESIGN.md`

### Component Style
- ขอบมน (rounded corners, ~6-8px), shadow เบาๆ (soft shadow) แยกการ์ดออกจากพื้นหลัง — ไม่ใช่สไตล์ขอบเหลี่ยม/เส้นขอบเรียบแบบเว็บ ref ต้นฉบับ
- หน้าตาโดยรวมอิง **shadcn/ui aesthetic** (การ์ด, ปุ่ม, ตาราง, modal ยืนยัน, badge สถานะ)
- **วิธี implement**: ใช้ Tailwind CSS ผ่าน CDN + เขียน component เองให้หน้าตาเหมือน shadcn/ui (ไม่ใช้ shadcn/ui ของจริง เพราะต้องมีระบบ build ซึ่งใช้ใน Artifact HTML ไฟล์เดียวไม่ได้) — class ของ Tailwind ที่เขียนไว้จะ copy ไปใช้ตอนโค้ดจริงภายหลังได้ตรงๆ

### Layout
- Sidebar ซ้าย (เมนูนำทางไปแต่ละหน้าจอ) + Top bar ด้านบน (ชื่อระบบ, ปุ่มสลับภาษา, user info)
- หลัง Login → เข้า **DashboardScreen** ก่อน แล้วค่อยเลือกเมนูจาก sidebar ไปหน้าอื่น
- **Responsive**: ต้องรองรับ tablet/mobile ด้วย ไม่ใช่ desktop อย่างเดียว — Sidebar ต้องยุบเป็นเมนูแบบ hamburger/drawer บนจอแคบ
  - แต่ให้ถ่วงน้ำหนักตาม `biz-requirement.md` ข้อ 10: **มือถือใช้เช็คสถานะเป็นหลัก** (ดูรายการ order, สถานะ, ผลการทำงาน) ส่วน**ฟอร์มตั้งค่ากฎ** (กฎ SKU, reorder threshold, สูตรต้นทุน, ข้อมูล supplier) ออกแบบให้ใช้งานจริงบน desktop เป็นหลัก — บนจอเล็กแค่ไม่พัง อ่านได้ ก็พอ ไม่ต้องฝืนทำให้กรอกสะดวกเท่า desktop

### Icon
ใช้ **Lucide icons** (โหลดผ่าน CDN) — เข้ากับ Tailwind/shadcn aesthetic เป็นมาตรฐานคู่กันอยู่แล้ว

## 6. Reference

### 6.1 `https://ui.shadcn.com` — **reference หลักของหน้าตา component และ layout dashboard**
ดูตัวอย่างหน้า Dashboard/Blocks ของ shadcn เป็นมาตรฐานของงานนี้: sidebar + stat card + ตาราง + badge + form
ที่สะอาด เรียบ มืออาชีพ ขอบมน shadow เบา ตัวหนังสือไม่ใหญ่เกิน เว้นระยะสม่ำเสมอ — **ให้ยึดระดับความเรียบ/ความเป็นระเบียบแบบนี้เป็นหลัก** เพราะเป็นระบบ admin ที่มีข้อมูลหนาแน่น

### 6.2 `https://www.spline.one` — reference ของ "ระดับความพรีเมียม" เท่านั้น
หยิบมาเฉพาะ: ความประณีตของ typography/ระยะห่าง, micro-interaction และ transition ที่ลื่นไหลตอน hover/เปลี่ยนหน้า, การใช้ gradient เป็นจุดเน้นเล็กๆ (ให้อยู่ในโทนน้ำเงินตาม palette ข้อ 4)

**ไม่เอา**: พื้นหลังมืด, งาน 3D/โมเดลลอย, สไตล์ landing page การตลาด — ระบบนี้เป็น internal admin tool ที่เน้นใช้งานจริง ไม่ใช่เว็บขายของ

### 6.3 `https://chula.hackathon.team1.quarkhadron.dev` — reference เสริมด้าน structure
สิ่งที่หยิบมาใช้ (เฉพาะ layout/structure ไม่ใช่สี):
- Header ใช้ตัวอักษรหนาสไตล์ flip-board/จอสนามบิน (เช่นคำว่า "SUBMISSIONS" ในภาพต้นฉบับ) สำหรับหัวข้อหน้า/section ใหญ่ๆ
- Ticker/info bar แนวนอนไล่ข้อมูลสั้นๆ ด้านบน (ปรับใช้เป็นแถบสรุปสถานะ/จำนวน order ด้านบน dashboard ได้)
- การ์ดขอบบาง เว้นระยะห่างเยอะ (generous whitespace)

สิ่งที่ **ไม่เอา**:
- โทนสีดำ (พื้นหลังเข้ม) + แดง (จุดเน้น) ของเว็บต้นฉบับ — ให้แทนที่ด้วย palette ในข้อ 4 แทน (ขาว/น้ำเงิน)
- ขอบเหลี่ยมคม/shadow เป็นศูนย์ — ให้ใช้ขอบมน+shadow เบาแทน (ข้อ 4)

> ลำดับความสำคัญเมื่อ reference ขัดกัน: **6.1 (shadcn) > 6.2 (ความพรีเมียม) > 6.3 (ลูกเล่น flip-board/ticker)** — ความอ่านง่ายและใช้งานจริงมาก่อนลูกเล่นเสมอ

## 9. Spec เพิ่มเติมที่ไม่ได้มาจาก UC

### 9.1 DashboardScreen — ต้องออกแบบเองทั้งหมด
หน้านี้**ไม่ได้ map กับ UC ไหน** จึงไม่มีข้อความบังคับใน use case description (ยกเว้นชื่อสถานะและปุ่ม "นำเข้า Order" ที่ต้องใช้คำตรงตาม UC) ให้มีองค์ประกอบดังนี้:

- **Ticker/info bar ด้านบน** — ตัวเลขสรุปวิ่งแนวนอน (จำนวน order แต่ละสถานะ, ยอดวันนี้) ตามสไตล์ข้อ 6.3
- **Stat cards** — การ์ดสรุปจำนวน order แยกตามสถานะสำคัญ เช่น "รอตรวจสอบคำสั่งซื้อ", "รอ Admin ตัดสินใจสั่งซื้อ", "รอส่งมอบ", "ยกเลิกแล้ว" (ใช้ชื่อสถานะจริงจาก UC และสี badge ตามข้อ 4)
- **ปุ่ม "นำเข้า Order"** (จาก UC 4A) + **การ์ดสถานะการเชื่อมต่อ Marketplace** แสดงสถานะการเชื่อมต่อของ Rakuten Ichiba (RMS) รองรับเคสเชื่อมต่อล้มเหลวตาม "ทางเลือก #1" ของ 4A (ข้อความ: "ไม่สามารถเชื่อมต่อกับ [ชื่อช่องทางขาย] ได้ กรุณาตรวจสอบการตั้งค่า")
- **ตาราง Order ล่าสุด** — พร้อม status badge และลิงก์กดเข้าไปยังหน้าที่เกี่ยวข้อง
- **Chart เล็กๆ 1–2 อัน** (เช่น จำนวน order ต่อวันย้อนหลัง 7 วัน) พอให้หน้าดูสมบูรณ์ ไม่ต้องซับซ้อน

เนื้อหาข้างบนครอบคลุมสิ่งที่เจ้าของธุรกิจอยากเห็นในหน้าจอหลักตาม `biz-requirement.md` ข้อ 12 ครบทั้ง 4 อย่าง: ออเดอร์ที่รอพิมพ์ label, สต๊อกต่ำกว่าเกณฑ์/สถานะ reorder, ต้นทุนต่อหน่วย, และ error/action ที่ล้มเหลว (ใช้สีเตือนให้สังเกตง่าย) — ทุกตัวดึงข้อมูลที่มี UC รองรับจริงทั้งหมด

> ❌ **เคยพิจารณาแล้วตัดออก**: ไอคอนกระดิ่งแจ้งเตือนใน topbar และการ์ด daily summary — เพราะไม่มี UC ไหนรองรับ (คำว่า "แจ้งเตือน" ใน use case description ทั้ง 46 จุดเป็น inline error/warning message ในแต่ละหน้า ไม่ใช่ศูนย์รวมแจ้งเตือน) **อย่าเพิ่มกลับเข้ามา**

### 9.4 State ที่ต้องออกแบบให้ครบทุกหน้า

## 10. Output Design — 2 Reports (rubric ข้อ 31)

รูบริกข้อ 31 บังคับว่า "แสดงรายงานทั้งหมดในระบบ (**2 reports**) — แสดงโครงสร้างของ report และตัวอย่างของรายงานที่ได้บันทึกข้อมูลผ่าน uc ต่างๆ"
และข้อ 33 (การทดสอบ) ยังระบุให้ capture screen "การบันทึกและ**การออกรายงาน**" ด้วย

ทั้ง 2 รายงานทำเป็น **print view** ที่เปิดจากหน้าจอเดิม (ไม่นับเป็นหน้าจอใหม่ ยังคง 12 หน้า) เวลาพิมพ์ให้ซ่อน sidebar/topbar

### รายงานที่ 1 — ใบปะสินค้า (Shipping Label)
- **ที่มา**: UC 6S (จัดรูปแบบใบปะสินค้า) + UC 9A (พิมพ์ใบปะสินค้า) · เปิดจาก **LabelPrintScreen**
- **โครงสร้างฟิลด์** อิง `Q6S.2` ที่ INSERT ลงตาราง `label`: `label_template`, `rsl_no`, `parcel_seq`, `parcel_total`, `label_status`, `created_at` บวกข้อมูลผู้รับและรายการสินค้าจากตาราง `orders`
- **หน้าตา**: เลย์เอาต์สำหรับพิมพ์จริงขนาดใบปะหน้าพัสดุ — ที่อยู่ผู้รับ, เลข RSL, ลำดับกล่อง (เช่น 1/3), SKU/จำนวน, barcode/เลขอ้างอิง

### รายงานที่ 2 — รายงานต้นทุนต่อหน่วย (Unit Cost Report)
- **ที่มา**: UC 4S (คำนวณ Cost ในการสั่งสินค้าเติม stock) · เปิดจาก **CostCalculatorScreen**
- **โครงสร้าง** อิงสูตร `Q5.2`:
  ```
  Unit Cost = ((purchase_price × exchange_rate) + intl_freight + duty_fee) / order_qty
              + marketplace_fee + domestic_shipping + rsl_charge
  ```
  แสดง cost component แยกบรรทัดให้เห็นที่มาของตัวเลขทุกตัว แล้วสรุปเป็นต้นทุนต่อหน่วยด้านล่าง
- ข้อมูลผลลัพธ์ที่บันทึกไว้มาจาก `Q5.3` (cost log) ใช้แสดงประวัติการคำนวณย้อนหลังได้
- **หน้าตา**: ตารางรายการต้นทุนพร้อมหัวรายงาน (SKU, ชื่อสินค้า, วันที่คำนวณ, อัตราแลกเปลี่ยนที่ใช้) และบรรทัดสรุปต้นทุนต่อหน่วยเน้นชัด
