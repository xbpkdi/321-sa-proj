## ปัญหาที่ 1 — Actor ผิด: UC อัตโนมัติถูกผูกกับ "เจ้าของ" เหมือนเป็น manual

**ทำไมถึงเป็นปัญหา:** `biz-requirement.md` ข้อ 3.1 ระบุชัดว่าเป้าหมายหลักคือ "ใช้ Codex สร้างระบบ**อัตโนมัติ** 3 อย่าง" และข้อ 5 (ตาราง To-Be Workflow) เขียนไว้ตรงๆ ว่าทั้ง 3 ฟังก์ชันทำงานอัตโนมัติ ไม่ใช่ให้เจ้าของกดเอง:

| ฟังก์ชัน | Trigger ตาม biz-requirement | UC ปัจจุบันที่ผูกผิด actor |
|---|---|---|
| Auto Label Printing | "ดึงออเดอร์จาก Rakuten RMS → ... → พิมพ์ label **อัตโนมัติ**" | UC6 พิมพ์ใบปะสินค้า |
| Auto Reorder | "ตรวจสต๊อกตามรอบ → เทียบ threshold → ส่งคำสั่งซื้อ...**โดยอัตโนมัติ**" | UC7 สั่งสินค้าจาก Supplier เติมเข้า stock |
| Unit Cost Calculator | "รวมต้นทุน... → คำนวณต้นทุนจริงต่อหน่วย" (คำนวณทุกครั้งที่มีข้อมูลใหม่ ไม่ใช่เจ้าของนั่งคิดเลขเอง) | UC5 ระบบคำนวณ Cost |
| ติดตามสต๊อกต่อเนื่อง | Action ข้อ 5: "ติดตามสต๊อกในบริษัทและ RSL **แบบต่อเนื่อง**" | UC3 เช็คสินค้าใน stock |

**หมายเหตุสำคัญ:** เจ้าของยังคง "ตั้งกฎ" ให้ระบบทำงาน (label rule, threshold, supplier, cost formula) และ "หยุด/แก้ไข action อัตโนมัติได้ทุกเมื่อ" (biz-requirement ข้อ 5) — นี่คือ use case คนละอันกับตัวการทำงานอัตโนมัติเอง เช่น "ตั้งกฎ SKU" (UC11) ยังคงเป็น manual ของเจ้าของถูกต้องแล้ว ไม่ต้องย้าย

### วิธีแก้
1. เพิ่ม actor ใหม่ชื่อ **"ระบบ (Scheduler)"** หรือ **"System"** (ใน UML มักวาดเป็น stick figure เหมือนกัน แต่บางที่ใช้สัญลักษณ์นาฬิกา/gear แทนก็ได้ ถ้า templateที่ใช้รองรับ)
2. ย้าย use case ต่อไปนี้จาก actor "เจ้าของ" ไปเป็น actor "ระบบ (Scheduler)":
   - UC5 ระบบคำนวณ Cost ในการสั่งสินค้าเติม stock
   - UC6 พิมพ์ใบปะสินค้า
   - ~~UC7 สั่งสินค้าจาก Supplier เติมเข้า stock~~ — **⚠️ อัปเดต ห้ามย้ายทั้งหมด** ดูหมายเหตุด้านล่าง
   - UC3 เช็คสินค้าใน stock (พิจารณาเปลี่ยนชื่อเป็น "ติดตามสต๊อกอย่างต่อเนื่อง" ให้สื่อว่าเป็น background job)
3. UC ที่เหลือของ "เจ้าของ" ที่เป็น manual จริง (ตั้งกฎ SKU, ยกเลิก Order, ตัดสินใจสั่งซื้อ ฯลฯ) คงไว้กับ actor เจ้าของตามเดิม

> **⚠️ อัปเดต 2026-09-15 — คอมเม้นอาจารย์เรื่อง Human-in-the-Loop:** อาจารย์คอมเม้นว่าไม่ชอบถ้าออกแบบให้ทุกอย่าง auto หมดตาม requirement ตรงๆ ควรมีจุดที่คนเข้ามาเกี่ยวข้อง (human-in-the-loop) โดยเฉพาะจุดที่กระทบเงิน — รายละเอียดเต็มดูที่ [`00-project-docs/summary.md`](../00-project-docs/summary.md) หัวข้อ 2
>
> **UC7 (Reorder) จึงห้ามย้ายไป actor "ระบบ" ทั้งหมด** เพราะเป็นจุดที่ commit เงินจริงกับ supplier — ให้แตกเป็น 2 UC แทน:
> - **UC7a "ระบบเสนอคำแนะนำสั่งซื้อเติมสต๊อก"** (actor: ระบบ) — คำนวณ/ร่างคำสั่งซื้อให้อัตโนมัติ ไม่ commit อะไร
> - **UC13 "ตัดสินใจการสั่งซื้อสินค้ามาเติม Stock..."** (actor: เจ้าของ) — **มีอยู่แล้วใน diagram ปัจจุบัน** เป็นจุด human approve ที่ถูกต้องอยู่แล้ว ต้องทำให้ชัดว่า flow บังคับผ่านจุดนี้เสมอก่อนจะส่ง order จริง (ไม่ใช่ทางเลือก/bypass ได้)
> - ส่วน UC5 (คำนวณ cost) และ UC6 (พิมพ์ label) ยังคงย้ายไป actor "ระบบ" แบบ auto เต็มได้ตามเดิม เพราะความเสี่ยงต่ำ ไม่ commit เงิน/ทรัพยากรจริง

## ปัญหาที่ 3 — ชื่อ UC ซ้ำกันข้าม actor โดยไม่ชัดทิศทาง

"อัพเดทสถานะการจัดส่ง" ปรากฏทั้งใน **เจ้าของ** (UC2) และ **Marketplace** (UC19) — ถ้าเป็นคนละทิศทางกันจริง (เช่น Marketplace ส่ง event เข้าระบบเรา VS ระบบเราส่ง status ออกไปอัพเดทที่ Marketplace) ต้องตั้งชื่อแยกให้ชัดว่าใครเป็นฝ่าย "ทำ" use case นั้น

### วิธีแก้ (เลือกแนวทางที่ตรงกับความเป็นจริงของระบบ)
- ถ้า **ระบบของเรา** เป็นฝ่ายส่งสถานะไปอัพเดทที่ Rakuten (เช่น หลัง delivery แจ้ง tracking no. กลับมา) → เปลี่ยนชื่อฝั่ง เจ้าของ/ระบบ เป็น **"ส่งอัพเดทสถานะการจัดส่งไปยัง Rakuten RMS"** (actor: ระบบ) และฝั่ง Marketplace ควรตัดออกหรือเปลี่ยนเป็น "รับการอัพเดทสถานะ" (แสดงว่า Marketplace เป็นปลายทาง ไม่ใช่ผู้เริ่ม)
- ถ้า **Marketplace** เป็นฝ่ายส่ง event/webhook สถานะมาเข้าระบบเราเอง (เช่น ลูกค้ายกเลิกออเดอร์ผ่าน Rakuten) → ชื่อฝั่ง Marketplace ควรเป็น **"ส่งอัพเดทสถานะออเดอร์เข้าระบบ"** และฝั่งเจ้าของ/ระบบเปลี่ยนเป็น "รับอัพเดทสถานะออเดอร์จาก Rakuten"

ทั้งสองแนวทางเป็นไปได้จริงในระบบนี้ (Rakuten ทั้งรับ status จากเราและส่ง event เข้ามา) — **ถ้าเกิดทั้งสองทิศทางจริง ให้แยกเป็น 2 UC คนละชื่อ** ไม่ใช้ชื่อเดียวกันซ้ำ

## ปัญหาที่ 4 — ชื่อ UC บางตัวยาวเกินไป ไม่ใช่ verb phrase สั้นกระชับ

ตามเกณฑ์ใน `todo/06-grading-rubric-checklist.md` ข้อ 6/9 (ใช้กับชื่อ Business Process แต่หลักการเดียวกันควรใช้กับชื่อ UC): ชื่อต้องเป็น verb อ่านแล้วเข้าใจทันทีว่าทำอะไร ไม่ใช่ประโยคอธิบายยาวๆ

- **UC13** "ตัดสินใจการสั่งซื้อสินค้ามาเติม Stock จากการคำนวณ Cost ที่ระบบคำนวณให้" — ยาวเกินไป
  - แนะนำเปลี่ยนเป็น **"อนุมัติคำสั่งซื้อเติมสต๊อก"** และย้ายรายละเอียด "จากการคำนวณ Cost ที่ระบบคำนวณให้" ไปเขียนใน pre-condition ของ Use Case Description แทน
  - พิจารณาด้วยว่า UC13 นี้ซ้ำซ้อนกับ UC7 (สั่งสินค้าจาก Supplier เติมเข้า stock) หรือไม่ — ถ้า reorder เป็น full-auto ตาม biz-requirement จริงๆ (ไม่ต้องรอเจ้าของอนุมัติ) UC13 อาจไม่จำเป็นต้องมีแยก หรือควรเปลี่ยนเป็น use case สำรอง (alternative case) ของ UC7 กรณีเจ้าของตั้งค่าให้ต้อง manual approve

## ปัญหาที่ 5 — ไม่มี actor "RSL" ทั้งที่เป็นระบบภายนอกหลัก

`biz-requirement.md` ข้อ 7.2 ระบุว่า RSL Inventory เป็นแหล่งข้อมูลสต๊อกหลักที่เชื่อมตรงกับระบบ (SKU เป็น key) และข้อ 1.2 บอกว่า "ใช้ RSL เป็นผู้ให้บริการ fulfillment" — ปัจจุบันไดอะแกรมพูดถึง RSL แค่ในชื่อ UC4 "จับคู่ Order กับ RSL" แต่ไม่มี actor RSL แยกออกมาเหมือน Delivery/Supplier/Marketplace ทั้งที่มีบทบาทเทียบเท่ากัน

### วิธีแก้
- พิจารณาเพิ่ม actor **"RSL"** ถ้าระบบต้องเรียก RSL API เพื่อดึง inventory หรือส่งคำสั่ง fulfillment โดยตรง (เช่น UC "ดึงข้อมูลสต๊อกจาก RSL")
- ถ้า RSL เป็นแค่ปลายทางข้อมูลที่ระบบเราไปดึงเอง (ไม่ใช่ actor ที่ initiate อะไรกลับมา) อาจไม่จำเป็นต้องมี actor แยก — แต่ต้องตัดสินใจให้ชัดตอนวาด ไม่ใช่ปล่อยคลุมเครือแบบตอนนี้ที่ RSL โผล่แค่ในชื่อ UC เดียว
