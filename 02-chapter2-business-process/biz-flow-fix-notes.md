## ปัญหาที่ 1 — ชื่อ UC ไม่ตรงกับเนื้อหาจริงของ process ที่มันครอบ

ตาม `todo/06-grading-rubric-checklist.md` ข้อ 13: "ชื่อต้องตรงกับรูป Business Process" — เจอจุดที่ไม่ตรงกัน:

| UC (ป้ายสีฟ้าใน rel-use-case) | Process ที่ครอบอยู่จริง | ปัญหา |
|---|---|---|
| 2. อัพเดทสถานะการจัดส่ง | "2. Update **จำนวนสินค้า**ใน Marketplace" | ชื่อ UC พูดเรื่อง "สถานะการจัดส่ง" แต่ process จริงพูดเรื่อง "จำนวนสินค้า/สต๊อก" คนละเรื่องกัน |

### วิธีแก้
เลือกอย่างใดอย่างหนึ่ง (ต้องดูว่าความจริงของระบบคืออะไร):
- **ถ้า process นี้คือการอัพเดทสต๊อกจริงๆ** → เปลี่ยนชื่อ UC จาก "อัพเดทสถานะการจัดส่ง" เป็น **"อัพเดทจำนวนสินค้าใน Marketplace"** ให้ตรงกับ process แล้วไปเช็คว่า use case diagram (`use-case.png`) กับ actor "Marketplace"/"เจ้าของ" ต้องแก้ชื่อตามด้วย
- **ถ้าจริงๆ ต้องมี 2 process แยกกัน** (อัพเดทจำนวนสินค้า กับ อัพเดทสถานะการจัดส่ง เป็นคนละขั้นตอน) → ต้องเพิ่ม process box ใหม่สำหรับ "อัพเดทสถานะการจัดส่ง" ที่แยกจาก process "Update จำนวนสินค้า" ที่มีอยู่แล้ว

## ปัญหาที่ 2 — Process 2 กล่องมีข้อความซ้ำกันเป๊ะ แต่ถูกครอบด้วยคนละ UC

Process box หมายเลข **8** และ **9** ทั้งคู่เขียนข้อความเหมือนกันเป๊ะว่า **"ส่งเลขติดตามการจัดส่งให้ Marketplace"** แต่:
- Process 9 ถูกครอบด้วย UC **"9. ส่งเลขติดตามสินค้าให้ลูกค้า"**
- Process 8 ถูกครอบด้วย UC **"15. ติดตามการจัดส่งให้ลูกค้า"**

ปัญหาซ้อนกัน 2 ชั้น:
1. Process 2 กล่องควรมีเนื้อหาต่างกัน (ไม่งั้นทำไมต้องมี 2 กล่อง) — ถ้าเป็นขั้นตอนเดียวกันจริงๆ ควรรวมเป็นกล่องเดียว ถ้าเป็นคนละขั้นตอน ต้องเขียนข้อความให้ต่างกันชัดเจน
2. ข้อความในกล่องบอกว่าส่งให้ **"Marketplace"** แต่ชื่อ UC ทั้งสองบอกว่าส่งให้ **"ลูกค้า"** — คนละผู้รับ ต้องเลือกให้ตรงกัน

### วิธีแก้ (ข้อเสนอ — ปรับตามความจริงของระบบ)
พิจารณาว่า flow จริงคือ: **Delivery ส่งเลขติดตามกลับมาที่ระบบเรา → ระบบส่งต่อเลขติดตามให้ลูกค้า (ผ่านช่องทางของ Rakuten) → และแยกอีกที ระบบอาจต้องอัพเดทสถานะกลับไปที่ Rakuten RMS ด้วย** ถ้าใช่ ให้แก้เป็น:
- Process 9: **"ส่งเลขติดตามสินค้าให้ลูกค้า (ผ่าน Rakuten)"** → ครอบด้วย UC9 "ส่งเลขติดตามสินค้าให้ลูกค้า" (ตรงกันแล้ว)
- Process 8: เปลี่ยนข้อความใหม่ให้สื่อความหมายของ UC15 "ติดตามการจัดส่งให้ลูกค้า" จริงๆ เช่น **"ติดตามสถานะการจัดส่งจนถึงลูกค้า"** (ไม่ใช่การ "ส่ง" อีกครั้ง แต่เป็นการ track/monitor สถานะต่อเนื่อง)

หรือถ้าตรวจสอบแล้วพบว่า 2 กล่องนี้ที่จริงคือ **ขั้นตอนเดียวกัน** (ทำซ้ำโดยไม่ตั้งใจตอน copy-paste กล่อง) → ให้รวมเหลือกล่องเดียว และพิจารณาว่า UC9 กับ UC15 ควรรวมเป็น UC เดียวกันหรือไม่

## ปัญหาที่ 3 — "จับคู่ Order กับ RSL" มี 2 เลข UC ขัดแย้งกัน (UC4 และ UC12)

ใน `biz-flow-rel-use-case.png` พบป้าย UC 2 อัน ที่ใช้ชื่อเดียวกันเกือบเป๊ะ:
- **"4. จับคู่ Order กับ RSL"** ครอบ process "4. Match เลข RSL กับ order_id (เตรียมจัดส่ง)" — อันนี้สมเหตุสมผล ชื่อตรงกับ process
- **"12. จับคู่ order กับ RSL"** ครอบ process "1. ดึง Order เข้าระบบ" + decision "มีกฎ SKU ที่ตรงกันในระบบไหม" — อันนี้ผิดปกติ เพราะ process ที่ครอบอยู่เกี่ยวกับการดึง order เข้าระบบและเช็คกฎ SKU ไม่ใช่การจับคู่กับ RSL

**ขัดแย้งเพิ่มเติมกับ `use-case.png`:** ในรายชื่อ UC ต้นฉบับที่ `use-case.png` ระบุว่า **UC12 ชื่อ "จับคู่ SKU"** ไม่ใช่ "จับคู่ order กับ RSL" — แปลว่าป้าย "12. จับคู่ order กับ RSL" ในไฟล์ rel-use-case น่าจะพิมพ์/แปะผิดชื่อ

### วิธีแก้
1. เปลี่ยนป้าย "12. จับคู่ order กับ RSL" (ที่ครอบ process ดึง order + เช็คกฎ SKU) เป็น **"12. จับคู่ SKU"** ให้ตรงกับ `use-case.png` และตรงกับเนื้อหา process ที่มันครอบจริง (เกี่ยวกับ SKU ไม่ใช่ RSL)
2. เหลือ **"4. จับคู่ Order กับ RSL"** ไว้ที่ process เดิม (Match เลข RSL) เพียงจุดเดียว ไม่ให้ชื่อนี้ซ้ำที่อื่นอีก
