# เอกสารความต้องการทางธุรกิจ (Business Requirements)
## โครงการระบบจัดการหลังบ้าน — เฟส 1: Rakuten Pilot
**บริษัท:** Colorado Co., Ltd.
**ขอบเขตเฟสนี้:** Rakuten Ichiba + Rakuten RMS + RSL (Rakuten Super Logistics) เท่านั้น
**แพลตฟอร์มอื่น (Yahoo! Auctions, Amazon):** จะพัฒนาในเฟสถัดไป ไม่รวมอยู่ในเฟสนี้

---

## 0. เหตุผลที่เลือก Rakuten เป็นแพลตฟอร์มนำร่อง

- เป็นช่องทางขายหลักที่มีข้อมูลออเดอร์จริงให้ทดสอบระบบได้ทันที
- ใช้ RSL (Rakuten Super Logistics) เป็นคลังสินค้าหลักอยู่แล้ว ซึ่งอยู่ใน ecosystem เดียวกับ Rakuten ทำให้เชื่อมข้อมูล order → stock → label ได้ลื่นไหลกว่า
- Rakuten RMS มีระบบ/API รองรับการดึงออเดอร์ การจัดการ label template และการเชื่อมสต๊อก ซึ่งครอบคลุม 3 ฟังก์ชันหลักที่ต้องการ
- ลดความเสี่ยงจากการเชื่อมหลายระบบพร้อมกันในรอบแรก

---

## 1. ภาพรวมธุรกิจ

**1.1 ธุรกิจ**
Colorado Co., Ltd. จำหน่ายสินค้านำเข้าและสินค้า OEM ผ่านมาร์เก็ตเพลสอีคอมเมิร์ซในญี่ปุ่น กลุ่มสินค้าหลัก ได้แก่ สินค้าอุปโภคทั่วไปนำเข้า อุปกรณ์ตกปลาและเหยื่อล่อ สินค้ากลางแจ้ง และยาดมสูดสมุนไพร (ya dom) นอกจากนี้ยังอยู่ระหว่างพัฒนาสินค้าออริจินัล ได้แก่ อุปกรณ์ตกปลา สินค้าฟิตเนส กรอบรูปไม้ และสินค้าสำหรับงานฉลองครบ 100 วันของทารก

**1.2 ขนาดกิจการ**
เริ่มต้นเป็นธุรกิจเสริมตั้งแต่ปี 2009 และแยกตัวเป็นธุรกิจอิสระในภายหลัง เจ้าของดูแลเองทั้งหมด ตั้งแต่วางแผนสินค้า จัดหา เจรจากับโรงงานต่างประเทศ การขาย การจัดส่ง และบริการลูกค้า โดยใช้ RSL เป็นผู้ให้บริการ fulfillment

**1.3 กลุ่มลูกค้า**
ผู้บริโภครายบุคคลที่ซื้อผ่าน Rakuten Ichiba (เฟสนี้), Yahoo! Auctions และ Amazon (เฟสถัดไป) กลุ่มเป้าหมายหลักคือผู้ใช้สินค้าตกปลา/กลางแจ้ง นักสะสมสติกเกอร์ และผู้ซื้อสินค้าอุปโภคทั่วไป

## 2. ปัญหาและแรงจูงใจ

**2.1 ปัญหาหลักในการดำเนินงานประจำวัน**
- พิมพ์ใบปะหน้าพัสดุ (shipping label) ด้วยมือหลังได้รับออเดอร์ทุกครั้ง
- ต้องเช็คสต๊อกข้ามหลายช่องทางและหลายคลัง (ในบริษัท + RSL) ด้วยตนเอง
- ตัดสินใจสั่งซื้อเพิ่ม (reorder) ด้วยความรู้สึก ไม่มีเกณฑ์ที่ชัดเจน
- คำนวณต้นทุนที่แท้จริงของสินค้าแต่ละชิ้นยาก เพราะต้องรวมหลายรายการ (ราคาซื้อ, อัตราแลกเปลี่ยน, ค่าขนส่งระหว่างประเทศ, ภาษีนำเข้า, ค่าธรรมเนียมมาร์เก็ตเพลส, ค่าส่งในประเทศ, ค่าธรรมเนียม RSL)

**2.2 งานที่ซ้ำซากและเสียเวลาที่สุด**
เช็คออเดอร์ใหม่ → พิมพ์ label → เช็คสต๊อก → เตรียม reorder → คำนวณต้นทุนสินค้า

**2.3 ผลกระทบที่เคยเกิดขึ้น**
- Binder เก็บสติกเกอร์ล็อตแรก 500 ชิ้น มีของเสียประมาณ 20 ชิ้น ต้องแก้ไขสเปค (ความหนาปก, ระบบล็อค, มาตรฐานรู, สี)
- ค่าส่งในบริษัทเองอยู่ที่ประมาณ 600 เยน เทียบกับคู่แข่งที่ประมาณ 200 เยน ขณะที่ RSL คิดค่า picking ประมาณ 60 เยนต่อชิ้น → ต้องหาสมดุลระหว่างต้นทุนขนส่งกับกำไร

## 3. เป้าหมายของแอปพลิเคชัน (เฟส 1 — Rakuten เท่านั้น)

**3.1 ผลลัพธ์สำคัญที่สุดถ้าระบบพร้อมใช้งานพรุ่งนี้**
ใช้ Codex สร้างระบบอัตโนมัติ 3 อย่าง สำหรับ **ออเดอร์ Rakuten**:
1. พิมพ์ shipping label อัตโนมัติทันทีที่ได้รับออเดอร์จาก Rakuten
2. สั่ง reorder อัตโนมัติเมื่อสต๊อกต่ำกว่าเกณฑ์ที่ตั้งไว้
3. คำนวณต้นทุนที่แท้จริงต่อหน่วยของสินค้าแต่ละ SKU ได้ง่ายและแม่นยำ

**3.2 ตัวชี้วัดความสำเร็จ (3 เดือนหลังเปิดใช้)**
- ออเดอร์ Rakuten ใหม่ทุกออเดอร์ได้ label ที่ถูกต้องโดยอัตโนมัติ
- สต๊อกต่ำกว่าเกณฑ์ทริกเกอร์ reorder ที่ถูกต้องโดยอัตโนมัติ
- คำนวณต้นทุน/กำไรต่อหน่วยได้เร็วและสม่ำเสมอ
- ลดขั้นตอนมือ ลดข้อผิดพลาดในการจัดส่ง ลดของขาดสต๊อก

## 4. Workflow ปัจจุบัน (As-Is) — เฉพาะเส้นทาง Rakuten

```
วิจัยตลาด/คู่แข่ง/รีวิว
   → วางแผนและเลือกสินค้า
   → ส่งสเปค (วัสดุ, ขนาด, สี, โลโก้, บรรจุภัณฑ์, MOQ) ให้โรงงานต่างประเทศ
   → รีวิวใบเสนอราคาและตัวอย่าง
   → สั่งผลิต นำเข้าสินค้า
   → สร้างภาพ/คำอธิบาย/หน้าขาย และลงขายบน Rakuten Ichiba
   → ลูกค้าสั่งซื้อและชำระเงินผ่าน Rakuten
   → จัดส่งจากบริษัทเองหรือผ่าน RSL
   → ติดตามข้อร้องเรียน/ของเสีย/คืนสินค้า/รีวิว/ยอดขาย
   → ปรับปรุงสินค้าและสั่งผลิตซ้ำ
```

**เครื่องมือที่ใช้อยู่:** Rakuten Ichiba, Rakuten RMS, RSL, ChatGPT (ร่างข้อความสื่อสารกับโรงงาน, คำนวณต้นทุน/ราคา/กำไร, จัดการสเปคสินค้า)

**จุดที่เกิดปัญหา/ความล่าช้า:**
1. หลังได้รับออเดอร์ — พิมพ์ label ด้วยมือ
2. ก่อน reorder — ต้องเช็คสต๊อกทั้งในบริษัทและ RSL
3. คำนวณต้นทุน — ต้องรวมหลายค่าใช้จ่ายแยกกัน

## 5. Workflow ที่ต้องการ (To-Be) — เฟส 1 Rakuten

| # | ฟังก์ชัน | รายละเอียด |
|---|---|---|
| 1 | Auto Label Printing | ดึงออเดอร์จาก Rakuten RMS → จับคู่กับ SKU, วิธีจัดส่ง, label template ที่ถูกต้อง → พิมพ์ label อัตโนมัติ |
| 2 | Auto Reorder | ตรวจสต๊อก (ในบริษัท + RSL) ตามรอบ → เทียบกับ threshold ที่ตั้งไว้ต่อ SKU → ส่งคำสั่งซื้อไปยัง supplier ที่กำหนดไว้ล่วงหน้าโดยอัตโนมัติ พร้อมบันทึกผลลัพธ์ |
| 3 | Unit Cost Calculator | รวมราคาซื้อ + อัตราแลกเปลี่ยน + ค่าขนส่งระหว่างประเทศ + ภาษีนำเข้า + ค่าธรรมเนียม Rakuten + ค่าส่งในประเทศ + ค่าธรรมเนียม RSL → คำนวณต้นทุนจริงต่อหน่วยและกำไรโดยประมาณ |

**สิ่งที่ยังคงทำด้วยมือ (นอกขอบเขต):** วางแผนสินค้า จัดหา เจรจาโรงงาน การตัดสินใจด้านคุณภาพ การอนุมัติขั้นสุดท้าย และกรณีลูกค้าพิเศษ — เจ้าของเป็นผู้กำหนดกฎ label/threshold/supplier/order quantity/cost formula และสามารถหยุดหรือแก้ไข action อัตโนมัติได้ทุกเมื่อ

## 6. ผู้ใช้งานและสิทธิ์

- **ผู้ใช้หลัก:** ตัวแทนบริษัท (เจ้าของ) — ดูแลทั้งระบบและตั้งค่ากฎทั้งหมด
- **บุคคลภายนอก:** RSL, โรงงาน/ซัพพลายเออร์ต่างประเทศ, ผู้ควบคุมการผลิต — ยังคงสื่อสารผ่านช่องทางเดิมของแต่ละฝ่าย ไม่ผูกเข้าระบบโดยตรงในเฟสนี้
- **ลูกค้าปลายทาง:** สั่งซื้อผ่าน Rakuten Ichiba ตามเดิม ไม่มีการสร้างระบบหน้าบ้านสำหรับลูกค้า

## 7. ข้อมูลที่ต้องจัดเก็บ (เฟส 1 — Rakuten)

**7.1 ฟิลด์ข้อมูลหลัก**
| กลุ่ม | ฟิลด์ |
|---|---|
| สินค้า | Product Name, SKU, Variation, Purchase Price, Currency |
| ออเดอร์ | Rakuten Order Number, Order Date, Product/SKU, Quantity, Delivery Address, Shipping Method |
| การจัดส่ง | Label Template, Label-Printing Status (Success/Fail) |
| สต๊อก | In-house Inventory, RSL Inventory, Reorder Threshold, Reorder Quantity |
| Reorder | Supplier, Lead Time, Reorder Status (Submitted/Failed) |
| ต้นทุน | Exchange Rate, International Freight, Duties, Rakuten Marketplace Fee, Domestic Shipping Cost, RSL Charges, Calculated Unit Cost |

**7.2 การเชื่อมโยงข้อมูล**
เชื่อมข้อมูลจาก Rakuten RMS, RSL, ไฟล์สต๊อกและไฟล์ต้นทุนที่มีอยู่ โดยใช้ **SKU เป็น key หลัก** ในการจับคู่ทุกระบบ

---

## 8. Action หลักในระบบ (เรียงตามลำดับความสำคัญ)

1. ดึงออเดอร์ใหม่จาก Rakuten RMS อัตโนมัติ
2. จับคู่ออเดอร์กับ SKU / วิธีจัดส่ง / label template ที่ถูกต้อง
3. พิมพ์ shipping label อัตโนมัติ
4. ตัดสต๊อกเมื่อออเดอร์ถูกประมวลผล
5. ติดตามสต๊อกในบริษัทและ RSL แบบต่อเนื่อง
6. ส่งคำสั่ง reorder อัตโนมัติไปยัง supplier เมื่อสต๊อกต่ำกว่า threshold
7. บันทึกผลลัพธ์ของการ reorder
8. คำนวณต้นทุนต่อหน่วยจากทุกองค์ประกอบที่เกี่ยวข้อง

---

## 9. การแจ้งเตือน

**แจ้งเตือนเฉพาะกรณีข้อยกเว้น/ผลลัพธ์สำคัญ เท่านั้น:**
- พิมพ์ label สำเร็จ / ล้มเหลว
- ส่ง reorder สำเร็จ / ล้มเหลว
- ข้อมูลสต๊อกขาดหายหรือไม่สอดคล้องกัน
- ข้อมูลต้นทุนที่จำเป็นขาดหาย

การประมวลผลปกติที่สำเร็จจะแสดงในรูปแบบสรุปประจำวัน (daily summary) ไม่ต้องแจ้งเตือนทีละรายการ

การสื่อสารกับลูกค้ายังคงผ่านระบบแจ้งเตือน/inquiry ของ Rakuten ตามเดิม ไม่อยู่ในขอบเขตของระบบนี้

## 10. การเข้าถึงระบบและความปลอดภัย

- **อุปกรณ์หลัก:** คอมพิวเตอร์ (ตั้งค่ากฎ label, threshold, supplier, cost formula) — มือถือใช้สำหรับเช็คสถานะเท่านั้น
- **บัญชีผู้ใช้:** มีบัญชี Admin สำหรับตัวแทนบริษัทเท่านั้น ไม่มีระบบบัญชีสำหรับลูกค้า
- **ข้อมูลที่ต้องป้องกัน:** ข้อมูลออเดอร์และที่อยู่จัดส่งของลูกค้า, ชื่อซัพพลายเออร์และราคาซื้อ, ข้อมูลต้นทุนสินค้า, credential ของ Rakuten/RSL, การตั้งค่า label, กฎ reorder อัตโนมัติ
- **มาตรการ:** เฉพาะ Admin เท่านั้นที่แก้ไข supplier / reorder quantity / threshold / cost formula ได้ และต้องใช้ 2FA (Two-Factor Authentication)

---

## 11. ราคาและการชำระเงิน

- การชำระเงินของลูกค้าดำเนินการผ่าน Rakuten ทั้งหมด ระบบนี้ **ไม่มีฟังก์ชันรับชำระเงิน**
- ระบบจะดึงเฉพาะข้อมูลออเดอร์ ค่าธรรมเนียม การคืนเงิน และข้อมูลจัดส่งที่จำเป็นต่อ 3 ฟังก์ชันหลักเท่านั้น
- การจ่ายเงินให้โรงงานต่างประเทศ (USD/CNY) ยังคงดำเนินการแยกนอกระบบ

## 12. ดีไซน์และหน้าจอหลัก

หน้าจอหลักของระบบควรแสดง ณ จุดเดียว (at a glance):
- ออเดอร์ Rakuten ที่รอพิมพ์ label / สถานะการพิมพ์
- สต๊อกที่ต่ำกว่าเกณฑ์ / สถานะการ reorder อัตโนมัติ
- ต้นทุนต่อหน่วยของแต่ละสินค้า
- ข้อผิดพลาดหรือ action ที่ล้มเหลว ควรมีสีเตือนให้สังเกตง่ายและแก้ไขได้ทันที

## 13. รายละเอียดการดำเนินงาน

- ปริมาณออเดอร์โดยประมาณ: สินค้ากลุ่ม binder เก็บสติกเกอร์ขายประมาณ 5–10 ชิ้น/วัน
- รอบจัดส่งในบริษัท: จันทร์ / พุธ / ศุกร์
- ของรางวัลรีวิว: จัดส่งภายใน 1 สัปดาห์หลังลูกค้าโพสต์รีวิว
- Deadline อื่น (พัฒนาสินค้า, เครื่องหมายการค้า) ดำเนินไปคู่ขนานนอกระบบนี้

## 15. หมายเหตุจากเจ้าของธุรกิจ

ธุรกิจหลักคือการค้าปลีก ไม่ใช่การพัฒนาแอปพลิเคชัน เริ่มต้นเป็นธุรกิจเสริมตั้งแต่ปี 2009 และดำเนินการอิสระในปัจจุบัน วัตถุประสงค์ของระบบนี้มีขอบเขตจำกัดและเน้นการใช้งานจริง: ใช้ Codex เพื่อพิมพ์ label อัตโนมัติเมื่อได้รับออเดอร์ สั่ง reorder อัตโนมัติเมื่อสต๊อกต่ำกว่าเกณฑ์ และทำให้การคำนวณต้นทุนต่อหน่วยสินค้าเป็นเรื่องง่าย การตัดสินใจทางธุรกิจอื่นๆ ยังคงอยู่ภายใต้การควบคุมโดยตรงของเจ้าของ
