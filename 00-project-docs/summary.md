## TL;DR

- **ทำได้จริงมั้ย:** ✅ **เช็คแล้ว (2026-09-15) — โดยหลักการทำได้** ทั้ง Rakuten RMS และ RSL (ฝั่งญี่ปุ่นที่ผูกกับ Rakuten Ichiba) มี Web API ให้ผู้ประกอบการที่เปิดร้านอยู่แล้วยื่นขอใช้งานได้จริง ไม่ใช่ทำไม่ได้ — แต่ไม่ใช่ API แบบเปิดสาธารณะ (self-serve ทันที) ต้องผ่านขั้นตอนยื่นคำขอ/อนุมัติก่อน และมี license key หมดอายุทุก 1 ปีต้องต่ออายุ รายละเอียดเต็มดูหัวข้อ 1.5
- **เรื่อง auto ทั้งหมด:** ต้องแก้ตามคอมเม้นอาจารย์ — ห้ามออกแบบให้ทุกอย่าง auto เงียบๆ โดยไม่มีคนเห็น ต้องมี **human-in-the-loop** อย่างน้อยตรงจุดที่มีผลกระทบทางการเงิน (ดูหัวข้อ 3) — ข่าวดีคือ diagram ที่มีอยู่ตอนนี้ (`use-case.png`) มี UC13 "ตัดสินใจการสั่งซื้อ..." ซึ่งเป็นจุด human-in-the-loop อยู่แล้ว แค่ต้องทำให้ชัดว่า flow ต้องผ่านจุดนี้เสมอ ไม่ใช่ทางเลือก

## 1.5 ผลการเช็ค Rakuten RMS API และ RSL API (ค้นเมื่อ 2026-09-15)

### Rakuten RMS Web Service API — ✅ มีจริง

- เป็น API ที่เปิดให้ **ผู้เปิดร้านบน Rakuten Ichiba** ใช้งานได้อย่างเป็นทางการ ("RMS Web Service") ครอบคลุมการจัดการสินค้า ออเดอร์ และสต๊อกผ่านโปรแกรม
- **ขั้นตอนขอใช้งาน:** ยื่นคำขอ API → ทางร้าน (merchant) จะได้รับอีเมล "API利用申請 承認のお願い" (คำขออนุมัติการใช้ API) → เข้าไปอนุมัติที่หน้า "WEB APIアクセス許可設定" ในระบบจัดการ RMS
- **ข้อมูลที่ต้องใช้เชื่อมต่อ:** Shop URL, Service Secret, License Key, และรายการฟีเจอร์ที่เปิดใช้งาน (ดูได้ในเมนู WEBAPIサービス ของ RMS)
- **ข้อควรระวัง:** License Key มีอายุ **1 ปีนับจากวันออก** ถ้าไม่ต่ออายุก่อนหมดอายุ การเชื่อมต่อจะหยุดทำงานทันที — ต้องมีระบบเตือนต่ออายุ ไม่ใช่ตั้งค่าแล้วปล่อยลืม
- มี client library ให้ใช้อ้างอิงแล้วหลายภาษา (.NET, Ruby) และมี MCP server ตัวอย่างที่ใช้ API นี้จริงด้วย

### RSL (Rakuten Super Logistics) — ✅ มี API แต่ต้องเช็คให้ชัดว่าเป็นตัวไหน

พบว่าชื่อ "Rakuten Super Logistics (RSL)" ถูกใช้กับ **2 บริการที่ไม่ใช่ระบบเดียวกัน**:

1. **RSL ฝั่งญี่ปุ่น** (เดิมคือ Rakuten Fulfillment Center เริ่มปี 2012) — เป็นบริการโลจิสติกส์ในเครือ Rakuten ที่ออกแบบมาสนับสนุนร้านค้าบน Rakuten Ichiba โดยเฉพาะ เชื่อมกับ RMS ได้ ("seamlessly connects with your Rakuten Ichiba store") มี API sync สต๊อก/ออเดอร์/tracking ใช้งานจริงผ่านเครื่องมือกลุ่ม EC一元管理 (เช่น NextEngine, TEMPOSTAR, BOSS) — ตัวนี้น่าจะเป็นตัวที่ **Colorado Co., Ltd. ใช้อยู่จริง** เพราะขายผ่าน Rakuten Ichiba
2. **RSL ฝั่งสหรัฐฯ** (เดิมชื่อ Webgistix ถูก Rakuten ซื้อกิจการ) — เป็น 3PL คนละระบบ มีคลังในนิวยอร์ก แอตแลนตา ลาสเวกัส ฯลฯ เชื่อมกับ ShipStation/Extensiv/Sellercloud สำหรับร้านค้าบน Amazon/eBay/Shopify — **ไม่เกี่ยวกับ Rakuten Ichiba โดยตรง**

**ทำไมสำคัญ:** ถ้าทีมงานหรือเจ้าของธุรกิจเข้าใจผิดว่าเป็น RSL ตัวเดียวกัน อาจไปเช็ค/สมัคร API ผิดระบบ หรือ mapping field ผิด (เช่น RSL สหรัฐฯ ใช้หน่วยที่อยู่/carrier แบบอเมริกา ไม่ตรงกับ flow ที่ต้องส่งในญี่ปุ่น) — **ต้องถามเจ้าของธุรกิจให้ชัดก่อนว่าใช้ RSL ตัวไหน** (แทบมั่นใจว่าเป็นตัวญี่ปุ่น เพราะขายผ่าน Rakuten Ichiba เป็นหลัก แต่ควรยืนยันไม่ใช่เดา)

## 2. คอมเม้นอาจารย์: Human-in-the-Loop

**สิ่งที่อาจารย์ไม่ชอบ:** ออกแบบระบบตาม requirement ตรงๆ แบบทุกอย่าง auto หมดโดยไม่มีคนเข้ามาเกี่ยวข้องเลย

**ทำไมสมเหตุสมผล:** ระบบที่ auto 100% ไม่มีจุดให้คนตรวจสอบเลยมีความเสี่ยงทางธุรกิจจริง (เช่น สั่งซื้อผิดจำนวน/ผิดราคาโดยไม่มีใครรู้จนเงินออกไปแล้ว) และในมุมวิชา SA การออกแบบที่ไม่มี actor คนเข้ามาปฏิสัมพันธ์เลยก็ทำให้วิเคราะห์ use case ได้จำกัดกว่า

### โมเดลที่แนะนำ: แบ่ง auto เป็น 3 ระดับตามความเสี่ยง

| ระดับ | ลักษณะ | ตัวอย่างจาก flow ข้อ 1 | การจัดการ |
|---|---|---|---|
| **1. Auto เต็ม** | ไม่ commit เงิน/ทรัพยากรจริง แก้ไขย้อนหลังได้ง่าย | ดึงออเดอร์, จับคู่ SKU, เช็คสต๊อก, คำนวณต้นทุน, พิมพ์ label, ตัดสต๊อก | ทำอัตโนมัติได้เลย ไม่ต้องรอคน |
| **2. Auto + Notify (override ได้)** | ผลกระทบต่ำ-กลาง แต่ควรให้เจ้าของเห็น | อัพเดทสถานะ/ส่งเลขติดตามให้ลูกค้า | ทำอัตโนมัติ แต่ขึ้น dashboard ให้เห็น + เจ้าของหยุด/แก้ไขได้ทุกเมื่อ (ตรงกับที่ biz-requirement.md ข้อ 5 ระบุไว้แล้ว) |
| **3. Auto-draft + Human Approve (บังคับ)** | มีผลกระทบทางการเงิน/ความสัมพันธ์กับคู่ค้า | **Reorder — สั่งซื้อสินค้าเติม stock** | ระบบเตรียม/คำนวณให้ทั้งหมด แต่ **ต้องรอเจ้าของกดอนุมัติก่อนเสมอ** ถึงจะส่ง order จริงไปหา supplier |

**✅ แก้แล้ว (2026-09-17):** `use-case-to-be.png` (ปัจจุบันคือ `2.11-use-case-diagram-to-be.png`) แยก actor "ระบบ" ออกมาถือ 7 UC สาย S ที่เป็น auto เต็ม (คำนวณ cost = `4S`, จัดรูปแบบ label = `6S`, ฯลฯ) ส่วนจุด reorder ยังคง human-in-the-loop ไว้ตามที่วิเคราะห์ไว้ในตารางข้างบน — มีเส้นประสีแดง "ต้องอนุมัติ (5A) ก่อน" กำกับไว้ระหว่าง `5A) ตัดสินใจการสั่งซื้อ` → `6A) สั่งซื้อสินค้าเพิ่มจาก supplier` เสมอ ห้ามให้ actor "ระบบ" ข้ามไปสั่งเอง
