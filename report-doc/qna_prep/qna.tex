  \item \textbf{ตอบตรง ๆ} ประโยคแรกคือคำตอบ
  \item \textbf{ให้หลักฐาน} เปิดหน้าในเล่ม เปิดสไลด์ หรือเปิดเว็บ 1 อย่าง

{\heavy\Large ประโยคที่ใช้ได้เลย}\par
\begin{itemize}
  \item \textbf{ไม่รู้คำตอบ} ``เรื่องนี้เรายังไม่ได้ออกแบบไว้ครับ/ค่ะ แต่ถ้าจะทำ จะเพิ่มที่...'' ห้ามเดาตัวเลขหรือแต่งว่าทำไปแล้ว
  \item \textbf{ถูกชี้จุดผิด} ``ขอบคุณครับ/ค่ะ จุดนี้เราพลาด จะแก้ให้ตรงกันในเล่มฉบับส่ง'' ยอมรับแล้วบอกวิธีแก้ ดีกว่าเถียง
  \item \textbf{ถามหลายข้อพร้อมกัน} ``ขอตอบทีละข้อนะครับ/คะ'' แล้วจดไว้
  \item \textbf{นอกขอบเขต} ``เรื่องนี้อยู่นอกเฟส 1 ที่ตกลงกับเจ้าของไว้ แต่ออกแบบให้ต่อได้ที่...''
  \item \textbf{เพื่อนตอบไม่ครบ} ``ขอเสริมนิดหนึ่งครับ/ค่ะ...'' แล้วพูดแค่ส่วนที่ขาด
\end{itemize}

{\heavy\Large ห้ามพูด}\par
\begin{tcolorbox}[colback=ink!6,colframe=ink!6,arc=4pt]
\begin{itemize}
  \item ``เจ้าของใช้เวลา 2 ชั่วโมงต่อวัน'' แบบไม่มีคำว่าประมาณ ตัวเลขเวลาทั้งหมดเป็น\textbf{ค่าประมาณ}จากขั้นตอนที่เจ้าของเล่า
  \item ``ระบบสั่งซื้อให้อัตโนมัติ'' ที่ถูกคือระบบ\textbf{เตรียม}ข้อมูลให้ แต่เจ้าของต้องกดตัดสินใจใน 5A และกดสั่งซื้อใน 6A เสมอ
  \item ``เว็บเก็บข้อมูลใน localStorage'' หรือ ``มี 15 ตาราง 63 SQL'' เป็นข้อมูลรุ่นเก่า ตอนนี้เว็บอ่านเขียน \textbf{PostgreSQL จริง 17 ตาราง} และ SQL ในเล่ม \textbf{113 ข้อ}
  \item ``มี Controller, Repository, Scheduler'' โค้ดจริงไม่มีคลาสเหล่านี้ ชั้นจริงคือ หน้าจอ $\rightarrow$ Server Action $\rightarrow$ use-case $\rightarrow$ queries $\rightarrow$ db.ts
  \item ``เชื่อม Rakuten RMS และ RSL แล้ว'' ที่ถูกคือเรียกผ่าน adapter ที่ตอนนี้เป็น\textbf{ตัวจำลอง (mock)} ทั้ง 6 ตัว
\end{itemize}
\end{tcolorbox}

\begin{q}{Please introduce the business in English \must}\label{q:english}
\tip{เกณฑ์การนำเสนอกำหนดให้แนะนำธุรกิจเป็นภาษาอังกฤษ ถ้าอาจารย์ขอให้พูดซ้ำหรือถามต่อเป็นภาษาอังกฤษ ใช้ 4 ประโยคนี้ พูดช้า ๆ}
\ans
\begin{itemize}
  \item ``Colorado Company Limited sells imported and OEM products on Rakuten Ichiba in Japan, such as fishing lures, outdoor goods and Thai herbal inhalers.''
  \item ``It started in 2009 as a side business and is run by one owner. Rakuten Super Logistics, or RSL, stores and ships the parcels.''
  \item ``Every order needs the same manual steps: check stock in two warehouses, match the order with RSL, print the label and send the tracking number. We estimate one to two hours a day.''
  \item ``Our system automates these repeated steps, but the owner still approves every purchase that spends money.''
\end{itemize}
\evidence{สไลด์ 3 (บทพูดอยู่ใน notes ของสไลด์), บทคัดย่อภาษาอังกฤษ}
\end{q}

\begin{q}{ทำไมเฟส 1 ทำแค่ Rakuten \must}\label{q:rakuten}
\ans
\begin{itemize}
  \item Rakuten Ichiba เป็นช่องทางขายหลัก มีคำสั่งซื้อจริงให้ทดสอบได้ทันที
  \item ร้านใช้ RSL เป็นคลังหลักอยู่แล้ว ซึ่งอยู่ในระบบเดียวกับ Rakuten จึงเชื่อมคำสั่งซื้อ สต๊อก และใบปะได้ต่อเนื่อง
  \item Rakuten RMS มี API ครอบคลุมทั้งดึงคำสั่งซื้อ รูปแบบใบปะ และสต๊อก ตรงกับ 3 งานหลัก
  \item ทำทีละแพลตฟอร์มลดความเสี่ยงจากการเชื่อมหลายระบบพร้อมกัน Yahoo! Auctions กับ Amazon อยู่เฟสถัดไป
\end{itemize}
\evidence{รายงาน 1.1 และ 1.5}
\end{q}

\begin{q}{ตัวเลข 1 ถึง 2 ชั่วโมงต่อวันมาจากไหน \must}\label{q:time}
\ans
\begin{itemize}
  \item มาจากจำนวนขายประมาณ \num{5 ถึง 10 ชิ้นต่อวัน} ตาม requirement คูณเวลาต่อคำสั่งซื้อประมาณ \num{12 นาที}
  \item 12 นาทีแยกเป็น 5 งาน ตรวจคำสั่งซื้อ 2 เช็กสต๊อก 3 จับคู่ RSL 2 จัดรูปแบบและพิมพ์ใบปะ 3 แจ้งเลขติดตาม 2 นาที
  \item ได้ \num{60 ถึง 120 นาทีต่อวัน} หรือ 30 ถึง 60 ชั่วโมงต่อเดือน ยังไม่รวมการคำนวณต้นทุน 20 ถึง 30 นาทีต่อครั้ง
  \item ตัวเลขเวลาเป็นค่าประมาณจากขั้นตอนที่เจ้าของเล่าตอนสัมภาษณ์ ยังไม่ได้จับเวลาจริง
\end{itemize}
\evidence{ตารางที่ 1-1 ในหัวข้อ 1.2, สไลด์ 4}
\careful{ตัวเลขที่ได้มาจากเจ้าของโดยตรงคือ 5--10 ชิ้นต่อวัน ค่าส่ง 600 กับ 200 เยน และค่า RSL 60 เยน ส่วนนาทีต่องานเป็นของเราประมาณเอง}
\end{q}

\begin{q}{ปัญหาไม่ใช่แค่ ``ไม่มีคอมพิวเตอร์'' หรือ}\label{q:notcomputer}
\ans
\begin{itemize}
  \item ไม่ใช่ครับ/ค่ะ เจ้าของใช้คอมพิวเตอร์และ Rakuten RMS อยู่แล้ว
  \item ปัญหาคือข้อมูลอยู่คนละที่ ต้องคัดลอกและเทียบเองทุกคำสั่งซื้อ เช่น สต๊อกอยู่ทั้งคลังบริษัทและ RSL ต้นทุนต้องรวม 8 ค่าเอง
  \item และตัดสินใจสั่งซื้อด้วยความรู้สึก ไม่มีจุดสั่งซื้อที่ชัดเจน
  \item ทุกปัญหาวัดได้ว่าลดลงหรือไม่ เช่น เวลาต่อวัน และเวลาคำนวณต้นทุน
\end{itemize}
\evidence{รายงาน 1.2 และ 2.3}
\end{q}

\begin{q}{วัดอย่างไรว่าระบบแก้ปัญหาได้จริง}\label{q:kpi}
\ans
ตั้งตัวชี้วัดไว้ภายใน 3 เดือนหลังเปิดใช้งาน 4 ข้อ
\begin{itemize}
  \item คำสั่งซื้อ Rakuten ใหม่\textbf{ทุกรายการ}ได้ใบปะที่ถูกต้องโดยไม่ต้องจัดรูปแบบเอง
  \item สต๊อกที่ต่ำกว่าเกณฑ์ถูกแจ้งเตือนครบทุก SKU
  \item คำนวณต้นทุนต่อหน่วยได้ภายใน \num{1 นาที} แทน 20 ถึง 30 นาที
  \item เวลางานหลังบ้านต่อวันลดลง\textbf{อย่างน้อยครึ่งหนึ่ง}จากตารางที่ 1-1
\end{itemize}
\evidence{รายงาน 1.3, สไลด์ 5}
\end{q}

\begin{q}{ขายแค่ 5 ถึง 10 ชิ้นต่อวัน คุ้มไหมที่จะทำระบบ}\label{q:worth}
\ans

\begin{q}{object ที่ติดกับ actor ใน Sequence Diagram คืออะไร \must}\label{q:screen}

\begin{itemize}

\begin{q}{โค้ดใช้ Server Action ไม่มีคลาส Controller ทำไมใน Sequence มี Screen และ Controller \must}\label{q:mvc}
\ans
\begin{itemize}
  \item Screen (ชั้น View) กับ Controller เป็น\textbf{ชื่อบทบาท (stereotype)} ตามแบบ MVC ที่อาจารย์สอน จับคู่กับไฟล์จริงหนึ่งต่อหนึ่ง ไม่ได้สร้างคลาสใหม่ในโค้ด
  \item Screen = \code{src/app/(app)/.../page.tsx} รับคลิกและแสดงผล
  \item Controller = Server Action ใน \code{src/app/(app)/actions.ts} เช่น \code{verifyOrderAction} ตรวจ session รับค่าจากหน้าจอ แล้วเรียก use-case Next.js ส่งคำขอจากหน้าจอมาที่ฟังก์ชันนี้ ทำหน้าที่เดียวกับ Controller
  \item Model = \code{src/lib/use-cases/*} (ลำดับขั้นของ UC) + \code{src/lib/queries/*} (SQL ค่าคงที่ \code{Q<UC>\_<n>}) และ \code{db.ts} คือ DBConnector
  \item วงเล็บใต้ชื่อ object ในรูปบอกชื่อไฟล์จริง เช่น \code{(actions.ts)} เปิดโค้ดเทียบได้ทันที
\end{itemize}
\evidence{สไลด์ 17, สไลด์ 44 (Layers), รายงาน 2.18 Class Diagram}
\tip{ห้ามพูดว่าโค้ดมีคลาส Controller หรือ Repository ให้พูดว่า ``Controller ในรูปคือ Server Action''}
\end{q}

\begin{q}{ทำไมไม่มีลูกศรส่งกลับไปที่ Actor \must}\label{q:noreturn}
\ans
\begin{itemize}
  \item Actor เป็นคน ไม่ใช่ object ในระบบ ระบบส่ง message ให้คนไม่ได้ สิ่งที่คนเห็นคือหน้าจอเปลี่ยน
  \item ผลลัพธ์จึงย้อนกลับเป็นเส้นประ (return) จาก DBConnector $\rightarrow$ Model $\rightarrow$ Controller $\rightarrow$ Screen แล้ว Screen แสดงผลเองเป็น \textbf{self message} เช่น \code{showSuccess()}, \code{showError(...)}
  \item ตามที่อาจารย์สอน และ \code{check\_diagrams.py} ตรวจทุก Sequence ว่าไม่มีเส้นที่ปลายทางเป็น Actor
  \item Use Case ที่ระบบทำเอง (S) ไม่มีหน้าจอของตัวเอง ผลขึ้นเป็นข้อความแจ้งเตือนในหน้าที่ Admin เปิดอยู่ ก็เป็น self message บน Screen เช่นกัน
\end{itemize}
\evidence{สไลด์ 17 บรรทัด \code{Screen ->> Screen : showSuccess()}, สไลด์ 21}
\end{q}

  \item สร้างด้วยสคริปต์ \code{gen\_collab.py} จาก mmd ของ Sequence จึงไม่หลุดกัน แล้ว render ด้วย Graphviz

\begin{q}{กันตัดสต๊อกซ้ำอย่างไร \must}\label{q:double}

\begin{q}{ระบบปลอดภัยแค่ไหน เก็บรหัสผ่านและ session อย่างไร \must}\label{q:security}
\ans
